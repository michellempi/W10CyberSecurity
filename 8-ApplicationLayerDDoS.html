Pengenalan

Topic Introduction — Mengenal Application Layer DDoS

Memahami apa itu DoS/DDoS, mengapa serangan pada lapisan aplikasi (OSI Layer 7) dapat melumpuhkan layanan tanpa memenuhi bandwidth jaringan, serta dampaknya pada toko online fiktif BelanjaKita.

Konsep Dasar & CIA Triad

Apa itu DoS dan DDoS?

Denial of Service (DoS) adalah upaya membuat layanan, server, atau sumber daya tidak tersedia bagi pengguna yang sah. Distributed Denial of Service (DDoS) memiliki tujuan serupa, tetapi trafik serangan dikirim secara serentak dari banyak perangkat yang terdistribusi.

Target utama serangan ini adalah aspek Availability (ketersediaan) dalam CIA Triad. Penyerang tidak perlu mencuri atau merusak data untuk menimbulkan kerugian besar: pelanggan cukup gagal membuka situs, mencari barang, login, atau menyelesaikan pembayaran.

OSI Layer 7

Apa itu Application Layer DDoS?

Application Layer DDoS adalah serangan pada lapisan aplikasi (OSI Layer 7) yang menyalahgunakan permintaan protokol aplikasi—dalam fokus modul ini adalah HTTP—untuk menguras sumber daya komputasi layanan.

Serangan ini tetap efektif meskipun bandwidth jaringan tidak penuh, karena paket HTTP yang datang tampak valid secara sintaks dan memaksa aplikasi serta backend memproses operasi berat dalam jumlah atau pola yang tidak wajar.

Analogi Sederhana

Analogi Kasir & Dapur Restoran

Bayangkan jalan raya menuju restoran (bandwidth jaringan) masih sangat lancar. Namun, ratusan orang masuk secara bersamaan dan memesan menu yang paling rumit dimasak satu per satu tanpa berniat makan.

Koki (CPU & worker) serta bahan di dapur (database) langsung kewalahan. Akibatnya, pelanggan sungguhan yang berdiri di antrean tidak bisa dilayani dan akhirnya pergi.

Permukaan Serang

Contoh Target pada Toko Online

  • Endpoint pencarian produk (/search?q=...) yang menjalankan query kompleks ke database.
  • Halaman katalog dengan proses filter kategori, rentang harga, dan sortir dinamis.
  • Endpoint login atau validasi yang memverifikasi kredensial dan sesi pengguna.
  • Formulir checkout atau pengiriman data yang memicu validasi stok dan transaksi backend.
Risiko Operasional & Bisnis

Mengapa Serangan Ini Berbahaya?

  • Website melambat drastis atau sama sekali tidak dapat diakses (HTTP 503 / timeout).
  • Pengguna sah gagal login, mencari produk, maupun menyelesaikan transaksi belanja.
  • CPU, memori, worker, pool koneksi, atau database mencapai batas kapasitas maksimum.
  • Perusahaan kehilangan pendapatan langsung, menanggung biaya mitigasi darurat, serta berisiko terkena penalti Service Level Agreement (SLA).
  • Pengalih perhatian (smokescreen): DDoS sering dijalankan untuk menyibukkan tim keamanan sementara penyerang melakukan intrusi lain di balik layar.
Capaian Modul

Tujuan Pembelajaran

  1. Menjelaskan DoS/DDoS dan hubungannya dengan aspek Availability.
  2. Membedakan serangan Application Layer dari serangan volumetrik dan protokol.
  3. Menjelaskan cara kerja HTTP GET Flood dan HTTP POST Flood.
  4. Mengidentifikasi dampak serangan terhadap web server, aplikasi, database, dan pengguna sah.
  5. Membaca indikator anomali trafik tanpa menyimpulkan DDoS hanya dari satu metrik tunggal.
  6. Memilih strategi mitigasi berlapis yang sesuai beserta keterbatasannya.

Konsep

Concept Explanation — Memahami HTTP GET & POST Flood

Membedah anatomi komunikasi HTTP, membandingkan mekanisme GET Flood dan POST Flood, serta menempatkan keduanya secara tepat dalam taksonomi serangan DDoS.

Protokol Request–Response (RFC 9110)

Dasar Komunikasi & Anatomi HTTP Request

HTTP adalah protokol request–response pada lapisan aplikasi. Klien (misalnya browser) mengirim request ke server, lalu server memprosesnya dan mengembalikan response berisi status code (seperti 200 OK atau 503 Service Unavailable) dan data.

4 Komponen Utama HTTP Request

  • Method: Tujuan operasi request, misalnya GET untuk meminta resource atau POST untuk mengirim data agar diproses.
  • Path / URL: Alamat endpoint yang dituju beserta parameter query string jika ada (contoh: /search?q=laptop).
  • Headers: Metadata komunikasi seperti Host, Content-Type, Authorization, dan User-Agent.
  • Body (Payload): Muatan data yang dikirim ke server; lazim digunakan pada metode POST (misalnya data formulir checkout).
Inspektor Paket · HTTP GET Request Method: GET 
GET /search?q=laptop&sort=price_asc&page=1 HTTP/1.1
Host: belanjakita.example
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html,application/json

# Tidak ada request body; parameter berada di URL/query string.
# Memicu query pencarian & pengurutan di database katalog.
Perbandingan Semantik & Perilaku
↙ GET ≠ selalu ringan, POST ≠ selalu berat

Perbedaan Metode HTTP GET dan POST

Aspek HTTP GET HTTP POST
Semantik standar Meminta representasi atau resource dari server. Meminta server memproses isi request sesuai resource target.
Data utama Umumnya parameter dikirim pada URL / query string. Umumnya data dikirim di dalam request body.
Penggunaan lazim Membuka halaman, mengambil katalog, pencarian produk. Mengirim formulir, login, checkout, membuat/memproses data.
Cache Response GET dapat di-cache jika aturan cache mengizinkan. Umumnya tidak diperlakukan seperti GET oleh cache standar.
Potensi beban Dapat berat bila endpoint menjalankan query atau pemrosesan mahal. Dapat berat bila body besar atau proses validasi/penyimpanan mahal.

Catatan Penting: GET tidak otomatis ringan dan POST tidak otomatis berat. Beban sebenarnya ditentukan oleh implementasi endpoint, ukuran data, konfigurasi caching, kompleksitas query, validasi, serta integrasi backend. Request GET ke pencarian kompleks bisa sangat mahal, sedangkan POST sederhana dapat ringan.

◆ Serangan 01

HTTP GET Flood

Serangan yang membanjiri server dengan request GET dalam jumlah atau pola tidak wajar menuju halaman atau endpoint yang memerlukan pemrosesan mahal.

Alur Konseptual

  1. Penyerang mengendalikan atau memanfaatkan banyak sumber request.
  2. Banyak request GET diarahkan ke endpoint dinamis tertentu.
  3. Web server menerima dan meneruskan request ke aplikasi.
  4. Aplikasi menjalankan pemrosesan, misalnya pencarian atau query database.
  5. CPU, worker, pool koneksi, dan database terbebani.
  6. Waktu respons melonjak; pengguna sah mengalami timeout atau error.
Contoh Ilustratif: Endpoint /search?q=laptop menjalankan pencarian dan filter berat. Ribuan request serupa secara bersamaan melampaui kapasitas pemrosesan backend.
■ Serangan 02

HTTP POST Flood

Serangan yang mengirim request POST dalam jumlah atau pola tidak wajar ke endpoint pemrosesan data, membawa body yang memicu validasi, parsing, atau penyimpanan backend.

Alur Konseptual

  1. Banyak request POST diarahkan ke endpoint formulir atau API.
  2. Server menerima header sekaligus membaca request body.
  3. Aplikasi memvalidasi serta memproses isi request.
  4. Proses backend mahal meningkatkan beban aplikasi dan database.
  5. Antrean dan kapasitas worker/koneksi menjadi penuh.
  6. Pengguna sah mengalami keterlambatan atau kegagalan transaksi.
Catatan Teknis: Ukuran body besar bukan syarat mutlak POST Flood—body kecil pun dapat melumpuhkan layanan jika memicu operasi backend mahal. Selain itu, POST Flood tidak selalu menghabiskan disk; dampaknya bergantung pada implementasi endpoint.
Ringkasan Pembeda

GET Flood vs POST Flood

Pembeda GET Flood POST Flood
Metode HTTP GET POST
Pola umum Meminta resource berulang kali Mengirim data / request body berulang kali
Contoh endpoint Search, katalog, halaman dinamis Form login, checkout, API pemrosesan
Potensi beban Rendering, query DB, cache miss, CPU Parsing body, validasi, proses bisnis, DB
Catatan Bisa ringan jika cache efektif; berat jika endpoint dinamis mahal Bisa ringan atau berat bergantung body dan proses backend

Baris yang disorot merupakan fokus website ini: serangan bekerja di OSI Layer 7 dan diukur melalui RPS (Requests per Second), waktu respons, serta utilisasi server.

Informasi Tambahan (Di Luar Fokus Utama): Pembanding Serangan HTTP Lambat — Slowloris & RUDY Klik untuk ringkasan

Fokus modul ini adalah HTTP GET & POST Flood ber-RPS tinggi. Sebagai pembanding singkat dalam keluarga Layer 7 DoS, serangan HTTP lambat bekerja menahan koneksi terbuka tanpa membanjiri RPS:

  • Slowloris: Mengirimkan header HTTP sedikit demi sedikit secara berkala agar koneksi tetap terbuka dan request tidak kunjung selesai.
  • R-U-Dead-Yet (RUDY): Mengirim POST dengan header Content-Length besar, tetapi menyalurkan isi body sangat lambat sehingga socket server tertahan.

1. Sumber trafik terbentuk

Penjelasan Singkat Metrik Simulator

RPS (Requests per Second)
Jumlah permintaan HTTP yang masuk ke server setiap detik. Lonjakan RPS dapat berasal dari serangan maupun dari promo sah (flash sale).
WU/s (Work Units per Second)
Satuan kapasitas kerja ilustratif dalam simulator untuk menggambarkan seberapa berat pekerjaan CPU/backend yang harus diselesaikan setiap detik.
CPU Load (Model)
Persentase beban prosesor server untuk mengeksekusi kode aplikasi, parsing request, dan validasi data.
Worker / Queue Utilization
Tingkat keterisian unit pekerja (worker) dan panjang antrean request yang menunggu giliran diproses saat server mulai sibuk.
Database Load (Model)
Tekanan beban pada sistem basis data akibat operasi pencarian (SELECT), filter katalog, maupun penulisan transaksi checkout.
Latency (Response Time)
Waktu tunggu (dalam milidetik) hingga pengguna menerima jawaban server. Latency naik tajam saat utilisasi mendekati atau melewati 100%.
HTTP 429 (Too Many Requests)
Kode status yang dikirim lapisan proteksi ketika jumlah request melewati ambang batas laju (rate limit) yang diizinkan. Pada simulator ini, seluruh request yang diblokir atau dibatasi disederhanakan sebagai HTTP 429; dalam implementasi nyata, respons dari WAF juga dapat berupa HTTP 403, HTTP 429, atau respons khusus sesuai konfigurasi sistem.
HTTP 503 (Service Unavailable)
Kode status ketika server kelebihan beban atau antrean penuh sehingga gagal melayani permintaan untuk sementara waktu.
Transparansi Logika Model

Rumus Demonstrasi (Bukan Rumus Universal)

  • Offered Work: (L × W_legit) + (A × W_attack)
  • Utilization: min(100%, Effective_Work / C × 100%)
  • Overload & Queue: Jika Effective_Work > C, kelebihan kerja menumpuk ke antrean (dibatasi maksimum agar grafik terbaca).
  • Latency Kurva Demo: Base × (1 + 4 × (Util/100)²) + penalti_antrean.

Catatan: Tidak semua HTTP 503 berarti serangan DDoS—lonjakan trafik sah atau gangguan backend internal juga dapat memicunya.

Checklist Investigasi · Slide 59

Membaca Indikator Anomali Trafik

CPU >95%, lonjakan RPS, atau dominasi HTTP 503 adalah petunjuk awal, bukan bukti tunggal DDoS. Korelasikan selalu dengan:

  • Apakah pola request menyimpang dari baseline harian?
  • Endpoint mana yang paling banyak diminta (mis. hanya /search)?
  • Apakah request berasal dari sumber IP atau User-Agent yang tidak biasa?
  • Apakah request sah juga melonjak (misalnya saat promo Flash Sale)?
  • Apakah rasio cache hit turun drastis?
  • Apakah error berasal dari aplikasi, database, atau jaringan?

Mitigasi

Security Countermeasures — Strategi Pertahanan Berlapis

Memahami pendekatan pertahanan berlapis (Defense-in-Depth) karena tidak ada satu kontrol tunggal yang mampu menahan semua pola serangan HTTP Flood tanpa efek samping.

Lapisan 01

1. Rate Limiting

Membatasi laju request dalam rentang waktu tertentu berdasarkan IP, sesi, atau endpoint (contoh: membatasi request berulang ke /search).

Kelebihan: Sederhana dan cepat menahan banjir dari satu sumber.

Keterbatasan: Botnet terdistribusi memakai ribuan IP; pengguna sah di balik NAT bersama dapat ikut terblokir.

Lapisan 02

2. Web Application Firewall (WAF)

Memeriksa HTTP request berdasarkan aturan, tanda tangan pola, reputasi sumber, dan karakteristik aplikasi sebelum mencapai backend.

Kelebihan: Mampu menyaring pola request otomatis yang menyimpang.

Keterbatasan: Memerlukan tuning aturan agar tidak memicu false positive; bukan pengganti optimasi kode aplikasi.

Lapisan 03

3. JS Challenge / CAPTCHA

Meminta bukti tambahan bahwa klien menjalankan browser sungguhan atau menilai perilaku interaksi untuk memisahkan bot dari manusia.

Kelebihan: Efektif menyaring skrip flood sederhana.

Keterbatasan: Mengganggu pengalaman pengguna jika diterapkan terus-menerus; bot modern dapat meniru browser.

Catatan Penerapan: Metode ini tidak selalu cocok diterapkan pada seluruh endpoint, terutama endpoint API dan AJAX, karena klien non-browser atau permintaan asinkron dapat gagal memproses tantangan sehingga komunikasi aplikasi terganggu. Penerapannya perlu disesuaikan dengan jenis endpoint dan kebutuhan aplikasi.

Lapisan 04

4. Caching & Optimasi Endpoint

Menyimpan hasil halaman/katalog yang aman di-cache, mengoptimalkan indeks database, membatasi hasil (pagination), serta menetapkan timeout dan batas ukuran body.

Dampak: Mengurangi biaya pemrosesan per request secara drastis di sisi origin.

Lapisan 05

5. Monitoring & Incident Response

Menetapkan baseline normal, memantau RPS, latency, CPU, worker, DB, cache hit, dan status HTTP, lalu mengaktifkan aturan mitigasi secara bertahap saat insiden terjadi.

Praktik Kunci: Dokumentasikan setiap perubahan aturan dan evaluasi false positive.

Lapisan 06

6. DDoS Scrubbing / Anycast

BGP Anycast Cloud Scrubbing menyebarkan dan menyaring trafik berskala besar sebelum mencapai server asal (origin).

Catatan: Lapisan tambahan infrastruktur jaringan; tetap harus dipadukan dengan WAF, rate limiting, caching, dan optimasi L7.

Laboratorium Kombinasi Kontrol

Kesimpulan Pembelajaran

Dari seluruh pembahasan dan simulasi mengenai Application Layer DDoS (HTTP GET & POST Flood), terdapat empat prinsip utama yang perlu diingat oleh praktisi maupun pemula keamanan siber:

  • Fokus pada Availability Layer 7: Serangan HTTP GET dan POST Flood melumpuhkan ketersediaan layanan dengan menghabiskan kapasitas CPU, worker, koneksi, dan database tanpa harus memenuhi kapasitas bandwidth jaringan.
  • Beban Ditentukan Implementasi Endpoint: Metode GET tidak selalu ringan dan POST tidak selalu berat; tingkat konsumsi sumber daya bergantung pada query database, validasi bisnis, ukuran payload, serta efektivitas caching pada endpoint target.
  • Korelasikan Banyak Metrik Sebelum Bertindak: Lonjakan RPS, CPU tinggi, atau munculnya status HTTP 503 bukan bukti tunggal DDoS, karena lonjakan trafik sah seperti flash sale juga dapat memicu gejala serupa.
  • Pertahanan Berlapis (Defense-in-Depth): Mitigasi yang efektif memadukan rate limiting, WAF, JavaScript challenge, caching, dan optimasi kode backend sambil tetap memperhitungkan risiko false positive terhadap pengguna sah.
